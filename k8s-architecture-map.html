Diagram 1 · The big picture

Master architecture — every subsystem at once

Everything ShopFast runs, grouped: who talks to the cluster, how images are built and delivered, the cloud underneath, the control plane brain, the cluster add-ons, and the worker nodes where pods actually run. Solid arrows are live traffic; dotted arrows are the watch/reconcile control relationships. Hover every box — this one diagram carries ~35 tooltips.

Tip: the single most important idea here — every component talks only to the kube-apiserver, and only the apiserver talks to etcd.
Diagram 2 · Control flow

What actually happens on kubectl apply

  1. ①–③ Request is authenticated, authorized (RBAC), then run through admission webhooks.
  2. ④–⑤ apiserver validates and writes the Deployment to etcd — only now does it “exist”.
  3. ⑥–⑧ Deployment controller → ReplicaSet controller → 3 Pending Pod objects (no node yet).
  4. ⑨ Scheduler binds each pod to a node (just writes spec.nodeName).
  5. ⑩–⑫ kubelet on that node pulls the image via containerd, starts it, reports Running back up.
Diagram 3 · Node-level detail

Scheduling decision + container startup (and where Docker fits)

  1. ①–③ Scheduler filters nodes that can’t fit, scores the rest, and binds the winner.
  2. Build lane shows the truth about Docker: it builds the image in CI; the cluster runs containerd, not Docker.
  3. ④–⑦ kubelet → containerd pulls image → creates the pause sandbox → CNI assigns the pod IP.
  4. ⑧–⑪ init containers → app containers → probes → Ready → added to the Service’s EndpointSlice.
Diagram 4 · Networking

How a request reaches a pod, and how pods reach each other

  1. ①–⑦ (north-south) user → DNS → cloud LB → Ingress Controller → Service → kube-proxy DNAT → pod.
  2. Ⓐ–Ⓒ (east-west) api pod → CoreDNS lookup → Postgres Service → Postgres pod.
  3. NetworkPolicy is enforced by the CNI, not the apiserver — no CNI support = silently ignored.
Diagram 5 · Storage

Dynamic persistent storage for a StatefulSet

  1. ①–③ StatefulSet’s volumeClaimTemplate creates a PVC that references a StorageClass.
  2. ④–⑥ CSI controller calls the cloud API, an EBS volume is created, a PV is auto-made and bound.
  3. ⑦–⑧ CSI node plugin attaches + mounts the disk into the pod; data survives reschedules.
Diagram 6 · Delivery

CI/CD + GitOps — from git push to running pods

  1. ①–⑥ build (Docker) → test → scan → sign → push to registry.
  2. ⑦–⑧ CI bumps the image tag in the config repo (a PR) — it never kubectl applys to prod.
  3. ⑨–⑫ Argo CD detects the drift, applies via apiserver, admission verifies the signature, rolling update.
  4. Rollback = a git revert; Argo re-syncs to the last known-good tag.
Diagram 7 · Elasticity

Autoscaling + observability — how the cluster reacts to load

  1. ①–④ cAdvisor → metrics-server → HPA computes desired replicas → Deployment scales pods up.
  2. Ⓐ–Ⓒ if pods don’t fit, they go Pending → Cluster Autoscaler/Karpenter adds a node.
  3. ⓧ–ⓩ exporters → Prometheus (history) → Grafana + Alertmanager → PagerDuty; alert on symptoms.
